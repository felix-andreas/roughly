## Usage

The easiest way to use Roughly is through its VS Code extension.

If you want to integrate Roughly with another editor that supports the Language Server Protocol (LSP), you can start the language server directly:

```sh
roughly server
```

## Features

Roughly supports the following language server features. Items marked 🧪 are experimental; items
marked ⚠️ are planned but not yet available.

- **Navigation**
  - Index of global variables and S4 / R6 classes and methods
  - Document symbol search — <kbd>Ctrl</kbd> + <kbd>Shift</kbd> + <kbd>O</kbd> *in VS Code*
  - Workspace symbol search — <kbd>Ctrl</kbd> + <kbd>T</kbd> *in VS Code*
  - Go to definition, including type names inside `#:` annotations
  - Go to type definition
  - Find all references
  - Document highlights (all occurrences of the symbol under the cursor)
  - Folding ranges for braced regions, argument lists, and comment blocks

- **Editing**
  - Completion for local and global variables
  - Completion for standard-library names, with their typed signatures as detail
  - Completion for record fields after `$` and for field strings inside `[["..."]]`
  - Rename variables across the whole workspace
  - Signature help
  - Inlay hints for inferred types
  - Semantic highlighting of `#:` type annotations — types, type parameters, parameter names,
    operators, and `@`-directives get distinct, theme-respecting colors (see the editor sections
    below for setup)

- **Formatting**
  - Format an entire document
  - Format a selected range *(🧪 experimental — enable with the `range_formatting` flag)*

- **Diagnostics**
  - Syntax errors — including missing or trailing commas
  - Lint rules — *[full list](/linter#semantics-checks)*
  - Unused local variables — *opt-in via `[check] unused = true`*
  - Type errors and function-call argument mismatches — *opt-in via `[check] typing = true`*
  - Undefined-variable errors *(🧪 experimental)*

Type *inference* runs by default and powers hover and inlay hints with no configuration. The two
opt-in diagnostics above only control what `roughly check` reports. See the
[Typing guide](/typing) for the inference model — structural and nominal types, function
types, unions, and generics with bounds, all written in [`#:` comments](/typing).

### Diagnostics delivery

Roughly implements the LSP **pull** diagnostics model (`textDocument/diagnostic`) and advertises
`inter_file_dependencies`, so an edit that moves diagnostics in dependent files is reflected when
those files are pulled. Each report carries a content-hash `resultId`; if the client sends back a
matching `previousResultId`, the server answers `Unchanged` instead of resending the items.

Delivery is negotiated at startup: when the client advertises pull-diagnostics support it owns the
request cadence, and the server stops pushing `publishDiagnostics`. Clients without pull support keep
receiving pushed diagnostics. Workspace-wide pull (`workspace/diagnostic`) is not yet implemented.

If an edit arrives while a pull is being computed, the server abandons the stale computation and
answers `ServerCancelled` with `retriggerRequest: true`, so the client re-pulls instead of caching
an incomplete report. A rename request cancelled the same way answers `ContentModified` rather than
an empty edit.

### Untitled and virtual documents

Documents whose URI has no `file:` path — for example a VS Code untitled buffer with the R language
mode — are served as standalone script documents: diagnostics, hover, completion, formatting, and
the other document features work as for any open file. Like all scripts, they export nothing to
package analysis.

## Planned

Not yet available:

## Supported Editors

Roughly is a standard LSP implementation and works with any editor that speaks LSP:

- **VS Code** — full support via the [dedicated extension](https://marketplace.visualstudio.com/items?itemName=felix-andreas.roughly)
- **Zed** — via the [Zed extension](https://zed.dev/extensions/roughly), alongside the R extension
  (see [Zed Extension](#zed-extension))
- **Other editors** — point your LSP client at `roughly server`

## VS Code Extension

### Installation

The easiest way to install is from the [VS Code Marketplace](/getting-started#vs-code-recommended). To
install a specific build manually:

<Steps>

1. Download the latest `roughly.vsix` from [GitHub Releases](https://github.com/felix-andreas/roughly/releases)
2. Install the extension in VS Code:
   ```sh
   code --install-extension roughly.vsix
   ```
3. Configure the extension by setting the path to the Roughly binary in `settings.json`:
   ```json
   {
     "roughly.path": "/path/to/roughly"
   }
   ```

</Steps>

### Building from Source

If you prefer to build the extension yourself:

```sh
# From the repository root
bun run package
code --install-extension roughly.vsix
```

### Configuration

You can customize the Roughly extension in VS Code through the following settings:

```jsonc
{
  // Use a custom binary instead of the bundled one
  "roughly.path": "/path/to/roughly",
  // Pass custom arguments; defaults to ["server"]
  "roughly.args": ["server", "--verbose"],
  // Enable experimental features (currently only range formatting)
  "roughly.experimentalFeatures": ["range_formatting"],
}
```

### Annotation highlighting

Inside `#:` comments, types, type parameters, parameter names, operators, and `@`-directives are
colored distinctly instead of rendering as plain comment text. This needs no configuration and
respects your color theme.

Two mechanisms cooperate:

- **LSP semantic tokens** (on by default in VS Code): the server classifies the annotation notation
  and emits the standard `type`, `typeParameter`, `parameter`, `operator`, and `decorator` token
  types.
- **A TextMate injection grammar** bundled with the extension colors the same notation wherever
  semantic tokens don't reach — for example when a theme disables semantic highlighting — and adds
  colors for punctuation the semantic tokens skip (union `|`, brackets, commas).

### VS Code Commands

Roughly's VS Code extension provides several commands to manage the language server:

- **Start Language Server**: Manually start the language server if it's not running
- **Stop Language Server**: Manually stop the language server
- **Restart Language Server**: Restart the language server (useful after configuration changes)
- **Open Logs**: View the language server logs for troubleshooting
- **Status Bar Integration**: Shows the current status of the language server and allows quick access to commands by clicking on the status indicator

## Zed Extension

The [Roughly extension for Zed](https://zed.dev/extensions/roughly) provides the language server for
R files.

Zed has no built-in R support, so install the [R extension](https://zed.dev/extensions/r) first — it
registers the R language and its tree-sitter grammar, and Roughly's extension attaches the language
server to that language. The `roughly` binary is found on your `PATH` or downloaded automatically
from GitHub Releases; to use a specific binary, set it in your `settings.json`:

```json
{
  "lsp": {
    "roughly": {
      "binary": { "path": "/path/to/roughly" }
    }
  }
}
```

### Annotation highlighting in Zed

Zed highlights code with tree-sitter, which treats a `#:` annotation as an ordinary comment. The
distinct colors for types, type parameters, parameter names, operators, and `@`-directives come from
the server via **LSP semantic tokens**, which Zed supports but leaves off by default. Enable them
for R in your `settings.json`:

```json
{
  "languages": {
    "R": {
      "semantic_tokens": "combined"
    }
  }
}
```

`"combined"` layers the server's tokens over Zed's tree-sitter highlighting. Since Roughly emits
semantic tokens only inside `#:` comments, everything else keeps its regular colors, and the
annotation colors follow your theme through Zed's standard semantic-token rules.
